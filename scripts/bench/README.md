# sccache benchmark harness

A repeatable measurement of sccache against a CMake + Ninja MSVC build, run at every
phase boundary so changes can be compared against a recorded baseline.

```powershell
cargo build --release -p sccache-bench

# defaults: generated project, 40 TUs, cache from $SCCACHE_DIR
.\target\release\sccache-bench.exe

# A/B compression against hit latency
.\target\release\sccache-bench.exe --zstd-level 1 --out results\zstd1.json

# against a real build tree
.\target\release\sccache-bench.exe --project D:\src\myproject --touch-file D:\src\myproject\include\core.h
```

Results are JSON under `results/`, which is gitignored — commit a baseline explicitly if
you want one tracked. A detailed log is written alongside it.

## Comparing two builds

**Put each binary in its own directory, both named `sccache.exe`. Do not rename them.**

sccache decides what it is from `argv[0]`: if the file stem is not exactly `sccache` it
treats itself as a compiler shim and rewrites the command line to
`sccache <exe-name> <args...>` (`src/cmdline.rs`). A binary named `sccache-before.exe`
therefore reads `--stop-server` as *"compile this"*, starts a daemon and blocks forever,
printing nothing. The harness refuses to run against a misnamed binary for this reason.

```powershell
mkdir target\bench-bin\before, target\bench-bin\after
copy <old build> target\bench-bin\before\sccache.exe
copy <new build> target\bench-bin\after\sccache.exe

.\target\release\sccache-bench.exe --sccache .\target\bench-bin\before\sccache.exe `
    --cache-dir D:\.cache\bench-before --out results\before.json
.\target\release\sccache-bench.exe --sccache .\target\bench-bin\after\sccache.exe `
    --cache-dir D:\.cache\bench-after  --out results\after.json
```

Use a separate cache directory per binary, or the second run starts warm.

## Scenarios

| | state going in | expectation |
|---|---|---|
| `cold` | empty cache, empty build tree | every TU misses |
| `cached` | warm cache, empty build tree | every TU hits |
| `touch` | warm cache, one hot header edited | everything including that header misses |

`cached` is the number that matters most: it is the steady state of a developer rebuild
and of CI with a warm cache.

## Not hanging, and saying so when it does

A benchmark that hangs is worse than one that fails — it burns wall clock and tells you
nothing. So every child process is supervised:

- **Heartbeat** (`--heartbeat`, default 10s) prints elapsed time and the child's most
  recent output line.
- **Stall detection** (`--stall`, default 30s) flags a child that has produced no output,
  and records the longest silence in the result even for runs that finish.
- **Hard timeout** (`--timeout`, default 900s) kills the child *and its descendants*
  (`taskkill /T`), records the scenario as timed out, and carries on. Killing only the
  direct child would leave ninja's compilers alive, holding the build and cache
  directories and poisoning the next scenario.

Logging goes through `tracing`, with `tracing_appender::non_blocking` handing every write
to a dedicated worker thread, so observation cannot perturb the timings being measured.
Writes go straight through rather than being buffered in user space, so a run that is
killed mid-flight still leaves a complete log — which is the only kind of run whose log is
interesting. `RUST_LOG` turns the level down for a noisy run.

Output is captured through a temp file rather than a pipe for anything that may spawn the
daemon. A daemonised process inherits the pipe handles; if nothing drains them it blocks
forever once the 64 KiB buffer fills, taking the daemon down with it and wedging every
later client. Ninja keeps pipes, since it does not daemonise and its output is wanted live.

## What the synthetic project is shaped like

Generated by `src/project.rs`, deterministic for given parameters — the same inputs always
produce byte-identical sources, so runs are comparable across machines.

Two shape decisions are load-bearing:

- **Headers pull in real standard library headers** (`<vector>`, `<string>`, `<map>`,
  `<sstream>`, …). In real C++ the preprocessor's cost is dominated by this, not by
  project code. A benchmark with cheap headers cannot tell you whether direct mode helps,
  because there is nothing expensive for it to skip.
- **One hot header is included by every TU**, so `touch` invalidates a known fraction
  rather than an arbitrary one.

Scale it with `--translation-units`, `--headers`, `--includes-per-unit`, `--weight`.
Absolute numbers from the synthetic project do not transfer to your build; use `--project`
for that. What does transfer is the *ratio* between scenarios and the direction of a change.

## Environment checks

These run before any timing and abort by default, because the usual failure is not a crash
but a silently invalid measurement:

- **Not a debug build.** sccache's hot path is blake3 hashing and zstd compression, and
  unoptimised Rust runs those far slower, swamping whatever is being measured. Hit/miss
  counters stay valid; timings do not.
- **Binary named `sccache`** — see above.
- **Cache and build tree on the same volume.** Required for ReFS block cloning, and
  cross-volume numbers are not comparable to same-volume ones.
- **Cache volume is ReFS**, and its Dev Drive trust state. Filesystem comes from
  `GetVolumeInformationW`, not `fsutil fsinfo`, which needs elevation — a check that
  silently degrades to "unknown" when unelevated is worse than no check. Dev Drive state
  genuinely does need elevation and is reported as `unknown (needs elevation)` rather than
  guessed.
- **`/Z7` reaches the compiler**, checked in `compile_commands.json`. Without embedded
  debug info MSVC writes a shared PDB and sccache refuses to cache at all
  (`"shared pdb"`), so the run would measure nothing.
- **Direct mode actually hits.** A fully cached rebuild that reports the mode enabled but
  zero preprocessor cache hits means every TU still ran the preprocessor. This is the
  regression test for the MSVC bug fixed in `9a58347` / `c36e2d6`; it was true of every
  MSVC build before those.

Pass `--skip-checks` to record findings and continue anyway. Findings are always written
to the JSON, flagged, so a compromised run is never mistaken for a clean one.

## Interpreting the counters

`preprocessor_cache_hits` and `preprocessor_cache_misses` count only compilations where
direct mode was actually in play. Both at zero therefore means the mode never engaged —
a different situation from engaging and missing, and worth checking before drawing any
conclusion from a cache-hit-rate number.
